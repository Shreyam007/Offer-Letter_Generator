OfferFlow HR — Interview Prep & Project Guide

A comprehensive, high-impact prep guide to help you explain the architecture, folders, and features of the **OfferFlow HR** bulk mail campaign system. It details file contexts, walkthrough scripts, and troubleshooting explanations for technical rounds.

📂 Part 1: Project Architecture Overview

OfferFlow HR is a bulk offer letter dispatch engine. It connects companies to their candidates by parsing spreadsheet data, letting users review/modify records in an interactive grid, customizing letter templates with rich variables, sending merged PDF/HTML offers through configured SMTP parameters, and tracking email delivery rates and open logs in real-time.

Core Stack: MongoDB (Database) | Express.js (REST Routing) | React.js (Component State) | Node.js (Async Execution) | Vanilla CSS (Design system & dark mode variables) | Nodemailer (Email Delivery).

📂 Part 2: What Contains What? (Folder Breakdown)

📁 Backend Directory Structure (/backend)

server.js — Express bootstrapper. Binds JSON and CORS middlewares, initializes database connectors, and opens the server listener.
config/db.js — Connects Node to the MongoDB database using Mongoose.
config/seed.js — Seeds base templates (Modern, Classic) if the template collection is empty on startup.
models/Company.js — Schema for verified organizations. Stores website address, logos, and encrypted SMTP configurations.
models/Template.js — Schema for letter styles. Details subject, body content with brackets, layout rules, and logo dimensions.
models/Candidate.js — Schema for recipients. Stores name, email, salary, custom CSV data, and dispatch status (Sent, Failed, Opened).
models/Campaign.js — Tracks sending batches. Maps total candidate rows, successful deliveries, and active template IDs.
routes/campaigns.js — Ingestion routing. Performs bulk upsert of CSV rows into candidate models and handles individual candidate record edits.
routes/email.js — Sending loop and diagnostics. Tests SMTP configurations and conducts async batch delivery. Also holds the tracking pixel request handler.

📁 Frontend Directory Structure (/frontend)

App.jsx — Layout framework. Switches screens across navigation tabs (Workflow, Archive, Settings) and sidebar controls.
index.css — Design engine. Contains theme custom properties (Light/Dark variables), layout rules, dynamic print scaling CSS, and custom scrollbars.
context/AppContext.jsx — Global state provider. Shares step progression, active campaign documents, list refreshes, and the theme context.
components/CsvUpload.jsx — Step 1: Upload. Captures candidate spreadsheets, parses headers using PapaParse on the client, and initializes the campaign.
components/DataReview.jsx — Step 2: Review. Visual spreadsheet grid allowing users to filter, search, delete, or edit candidate details inline.
components/TemplateEditor.jsx — Step 3: Edit. WYSIWYG editor supporting Modern, Classic, Minimal styles, variables shortcuts, HTML toggles, and scaled letter sheets preview.
components/PreviewSend.jsx — Step 4: Dispatch. Monitors mail merges, handles interval delay controls, and prints candidate PDFs on the client.
components/HistoryTab.jsx — Analytics logs dashboard showing dispatch outcomes, success rates, open metrics, and detailed audit trails.
components/SettingsTab.jsx — Settings panel for managing SMTP credentials, address credentials, and organization logo uploads.

📂 Part 3: Walkthrough Scripts for Key Coding Features

1. Candidate CSV Ingestion

Code location: frontend/src/components/CsvUpload.jsx

"Inside CsvUpload.jsx, we parse files on the client side with PapaParse. When parsing completes, we validate mandatory headers (Name, Email, Role, Salary, JoiningDate). If validated, we make a POST request to /api/campaigns, passing company and candidate arrays to create a campaign and bulk-upsert records using MongoDB's insertMany logic."

2. Asynchronous Mail Merge sending loop

Code location: backend/routes/email.js (Inside post route /send-campaign)

"In routes/email.js, the dispatch engine retrieves the campaign candidates. For each candidate, it performs a mail merge by replacing curly brace tags like {{Name}} with matching candidate fields. We establish a Nodemailer transporter using the company's decrypted SMTP configuration, loop through the recipients, send the emails, and update their statuses to 'Sent' or 'Failed' dynamically."

3. Real-Time Email Open Tracking (1x1 Transparent Pixel)

Code location: backend/routes/email.js (Tracking endpoint & Pixel injection)

"To track email opens, we append an image pixel tag: <img src="http://[host]/api/email/track/:candidateId.gif" width="1" height="1" /> to the bottom of the mail HTML. When the recipient opens the mail, the client requests the GIF. Our tracking endpoint updates the candidate model status to 'Opened' and registers the timestamp, then serves a raw transparent GIF buffer with Cache-Control headers set to prevent caching."

4. Client-side PDF Generation

Code location: frontend/src/components/PreviewSend.jsx

"We generate candidate PDFs directly on the client side using window.print() inside a sandboxed print frame. When a user clicks 'Download PDF', we isolate the rendered letter sheet element and trigger the print engine. This reduces CPU and memory overhead on our Node server."

📂 Part 4: How to Explain Key Troubleshooting Bug-Fixes

1. Fixing the Non-Scrollable Editor & Cut-off Textarea

The Bug: The template editor container had a fixed height constraint (calc(100vh - 118px)) and overflow: hidden. On smaller resolutions, this caused the Subject line, textarea editor, and Save buttons to be pushed off-screen and completely clipped without a way to scroll down.

How we resolved it:

  • We removed the restrictive fixed height and overflow: hidden on the outer container .template-editor-shell, allowing the page viewport to scroll naturally.
  • We configured .template-grid to use a safe min-height: 650px and a dynamic height (height: calc(100vh - 280px)). This guarantees the textarea editing region is always spacious (at least 350px tall), while scaling up beautifully on high-resolution screens.

2. Constraining Company Branding Logos

The Bug: When users uploaded large SVG company logos, the lack of sizing bounds in the branding container allowed SVGs to render at their default high resolution. This inflated the style bar card to be massive and pushed the text editor off-screen.

How we resolved it:

  • We introduced two target CSS wrappers: .logo-svg-wrapper and .logo-img-wrapper.
  • We modified the renderLogo helper in TemplateEditor.jsx to return these specific classes instead of generic utility tags.
  • In index.css, we bound the wrappers to a maximum of 32px by 32px inside the Branding toolbar. Now, large vector logos automatically scale down to fit the bar.

📂 Part 5: Common System Design Questions

Q: Why parse CSV on the client instead of uploading raw files to the backend?
A: Parsing client-side with PapaParse reduces file size payloads and saves server CPU cycles. It also allows us to show an interactive review table immediately (Step 2) so users can correct errors or remove duplicates before any data is sent to the database.

Q: Why serve a 1x1 transparent GIF instead of a PNG for tracking?
A: Transparent GIFs are the smallest possible graphic files (only 43 bytes). They are universally supported by 100% of email clients and prevent layout shifting or visual issues in the candidate's inbox.

Q: Why scale the letter sheet preview using CSS scale transform?
A: A4 proportions (610px by 780px) must remain fixed to guarantee that the preview accurately reflects the printed PDF layout. By utilizing transform: scale(...), we dynamically scale the preview down to fit smaller display areas without breaking line wraps, headers, or absolute positions inside the CSS template stylesheet.
